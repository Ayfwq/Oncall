1. 文档目的与产品定义
本文档是 Oncall AI SRE 从 0 到 1 开发的正式基线。后续需求、代码结构、接口设计和测试应以本文件为默认依据；变更核心架构必须新增 ADR，而不是在实现中隐式改变。
产品定义：Oncall 是一个持续监测本机多个服务项目、识别 Incident，并由统一 AI Agent 基于实时工具证据和运维知识库完成调查、解释、给出可执行处置方案与恢复验证，同时支持 Web/飞书持续追问的 AI SRE 平台。
核心能力
用户价值
完整 RAG
上传运维文档后，从 Docling 解析、清洗、结构化 Chunk、Hybrid Retrieval 到引用回答形成闭环。
运维对话
用户通过 Web/飞书咨询 SOP 或让 Agent 查询实时状态。
主动监测
系统无需用户提问即可周期采集、规则检测异常。
自主调查
发生 Incident 后，Agent 调多个只读 Tool 收集 Evidence、结合 RAG 判断根因。
完整故障报告
主动发送症状、证据、根因置信度、操作步骤、风险、验证步骤。
持续追问
Incident 报告同时是会话入口；用户继续追问时恢复 Incident Context。
持久多会话
像 ChatGPT 一样多会话；服务/电脑重启后历史仍在并可继续。
2. 范围、非目标与设计原则
2.1 V1 范围
单管理员用户；数据库预留 user_id，但不实现组织、多租户、RBAC。
本机多项目：Oncall 与被监控项目运行在同一 Windows 主机；支持进程、日志、Docker、PostgreSQL、HTTP 服务。
Agent 只读调查，不执行重启/杀进程/写 SQL 等有副作用操作。
Web 与飞书均可对话；飞书可主动接收 Incident 报告并在同一消息线程继续追问。
知识库支持 PDF/DOCX/PPTX/HTML/Markdown/TXT 等 Docling 可解析格式，具体 allowlist 以部署测试为准。
2.2 V1 非目标
远程 Linux/Windows Agent
企业多租户/SSO/RBAC
自动修复与无人审批动作
Prometheus/Grafana 强依赖
大规模日志全文存储平台
Kubernetes 自动发现
2.3 不可违反的设计原则
1. 检测是确定性代码，调查才使用 LLM。
2. 业务事实存 PostgreSQL；LangGraph checkpoint 不是业务数据库。
3. Milvus 是索引，不是知识原始事实源。
4. Agent 不拥有跨 project 任意切换权限；范围由运行时注入。
5. V1 无 destructive tools；未来动作必须 risk classification + explicit approval。
6. 所有 Agent 结论尽可能引用 Evidence；未知时明确“不确定”，禁止编造监控事实。
7. 所有重要异步工作必须 durable、幂等、可重试。

8. Monitoring Engine
APScheduler tick   -&gt; load enabled Projects   -&gt; collect enabled Integrations (parallel with timeout)   -&gt; normalize into SystemSnapshot   -&gt; persist compact metric samples / collector health   -&gt; Detector.evaluate(snapshot, rule_state)   -&gt; AlertEvents   -&gt; IncidentManager.apply(events)       -&gt; no incident: finish       -&gt; new FIRING: create Incident + Conversation + investigation job       -&gt; existing FIRING: update last_seen; usually no Agent rerun       -&gt; RESOLVED: close Incident + recovery notification
8.1 采集策略
默认周期 300 秒；每 Project 可配置 30 秒以上。V1 不支持小于 10 秒高频监控。
同一项目 6 类 Integration 并发采集，但每类独立 timeout；部分 collector 失败不使整轮 Snapshot 丢失。
SystemSnapshot 是压缩摘要；完整日志/进程详情不周期性复制，Agent 需要时通过 Tool 即时查。
metric_samples 默认 30 天 retention，可配置；聚合/清理作业每日执行。

10. Detector、Alert 与 Incident 生命周期
10.1 Rule State Machine
NORMAL -&gt; PENDING -&gt; FIRING -&gt; RECOVERING -&gt; NORMAL                |                        |                +---- still abnormal ---+trigger: threshold + consecutive_hitsrecovery: separate threshold + consecutive_recoveries (hysteresis)
字段
含义

连续命中次数，例如 2
recovery_threshold
低于/高于此恢复阈值才算恢复候选

连续恢复次数，例如 2

info/warning/critical

host / process target / container / db / endpoint
10.2 Incident 生命周期
OPEN -&gt; INVESTIGATING -&gt; DIAGNOSED -&gt; RESOLVED          \-&gt; FAILED (Agent run exhausted)Alert rule state 与 Incident business status 是两套状态，不混用。
Fingerprint：SHA-256(project_id | rule_id | resource_key | anomaly_type)。同一阈值的数值变化不创建新 Incident。
首次 FIRING：创建/合并 Incident，自动创建 Incident Conversation，enqueue incident_investigate。
持续 FIRING：只更新 last_seen 和新 AlertEvent；默认不每轮调用 Agent。
再调查：严重度升级、新关联异常/新证据、用户点“深度调查”、或超过默认 60 分钟 stale interval。
恢复：恢复条件成立后 status=RESOLVED，发送恢复通知，保留所有 Evidence/Diagnosis。

13.1 多会话持久化

13.2 Context Builder
数据库始终保存全部 Message；不会因为上下文裁剪而删除历史。
LLM 输入 = System Prompt + Project Context + Running Summary + Incident Context（若有）+ 最近消息 + 当前 Evidence + 本轮 RAG/Tool 结果。
当历史超过约 40 条消息或 12k tokens（两者任一）触发 summary job；实际阈值可调。
近期原始消息预算默认约 8k tokens，并根据当前模型 context_window 动态计算；不是固定截断条数。
若聊天流中断：Message 仍保存，agent_run 标记 INTERRUPTED；Web 提供“继续生成”，而不是丢失会话。

14.2 Ingestion Pipeline
1. Upload：扩展名 + MIME + 文件大小 allowlist，sanitize filename。
2. Checksum：SHA-256 去重；相同 scope + checksum 默认不重复入库。
3. Parse：rag-worker 调 Docling，输出统一 DoclingDocument。[R5][R7]
4. Normalize/Clean：去控制字符、冗余页眉页脚、重复空白；保留标题、编号、表格、代码块、来源页。
5. Canonicalize：保存 document.json 与 document.md。
6. Chunk：Docling HybridChunker baseline；SOP 结构边界优先。[R6]
7. Metadata：heading_path、section_type、page_range、scope、version 等。
8. Embedding：通过 EmbeddingGateway 生成 dense vectors。
9. Index：Milvus 写入 text + dense + BM25 function；成功后 document status=READY。[R8][R9]

14.4 Retrieval Pipeline
Agent query  -&gt; Rule-based normalize (service/error code/metric names preserved)  -&gt; metadata filter: [global OR current project]  -&gt; dense_top20  ||  bm25_top20  -&gt; RRF fusion / dedupe -&gt; candidate ~30  -&gt; reranker -&gt; top5  -&gt; relevance threshold  -&gt; CitationPackage  -&gt; if poor/no hit: one optional LLM rewrite -&gt; retry once
中文知识库必须为 BM25 配置并回归验证中文 analyzer/tokenizer；不能默认按英文分词效果推断质量。
每次检索记录 query、normalized query、召回 IDs、分数、rerank、最终引用，用于离线评估。
Embedding/Rerank/LLM 都通过 Profile Adapter 配置，不在业务代码硬编码模型名。

28. V1 验收标准
1. 用户在 Web 创建至少 3 个本机 Project，可分别配置进程/日志/Docker/PostgreSQL/HTTP。
2. Knowledge 页面上传 PDF/DOCX 等文档，解析/索引可见；聊天检索能返回可追溯引用。
3. Web 支持多个 Conversation；关闭 Oncall/重启电脑后历史列表和消息完整存在并可继续。
4. 普通 CHAT 可回答运维 SOP；需要实时信息时能调用对应 Tool，不凭空生成实时数据。
5. Monitoring 按周期生成 Snapshot，并基于规则/滞回创建与恢复 Incident。
6. 一次故障持续多个周期只形成一个 Incident，不因 CPU 88%-&gt;90% 重复创建/每轮调用 Agent。
7. 主动调查能在 budget 内使用多工具形成 Evidence，并生成结构化完整报告。
8. 报告包含：摘要、严重度、影响对象、症状、证据、根因+置信度、不确定性、具体解决步骤、风险、验证步骤、知识引用。
9. 飞书能主动收到报告；用户回复该报告后进入 FOLLOW_UP 并沿用 Incident Context。
10. V1 Agent 无法执行重启服务/杀进程/写数据库等操作。
11. 断开/重启 API、agent-worker、rag-worker 的恢复测试通过；任务不会静默丢失。
12. 所有重要链路可通过 request/conversation/incident/agent/tool IDs 追踪。

30.3 已修复的关键可靠性问题
Project “测试采集”使用 `persist_state=False`，不会推进正式日志 cursor。
Incident 持续 FIRING 时每轮刷新 `last_seen`；手工 resolve 会重置 detector state，因此仍异常时可以再次满足 trigger_for 后新建 Incident，不形成盲区。
真实模型决策上下文包含 8 个 Tool 的 description + 完整 JSON 参数 schema；project/incident scope 仍由 runtime 注入。 Executor 同时按稳定 schema 做运行时参数校验，拒绝模型注入 project_id 或超范围参数。
Notification 使用 pending/sent/suppressed/dead 状态、指数退避、max attempts、cooldown；resolved 不被 diagnosis cooldown 吞掉。
飞书入站事件使用 processing/processed/failed，业务失败不会在处理完成前永久标 processed。
monitor-worker 使用 PostgreSQL advisory lock，避免同一数据库同时启动多个采集 leader。
ToolRun 保存 result_size/truncated/error_code；RAG 保存 RetrievalTrace、chunk/version/page_range。
Knowledge upload 使用分块读取、大小上限、安全文件名和 owner scope，返回真实 durable job id。
生产环境校验 Master Key、默认管理员密码、真实模型 Key 与飞书凭证；LangGraph strict MsgPack 开关已进入配置模板。
Milvus collection 采用显式 knowledge index version；索引可由 canonical 文档源重建。
主动 Incident 调查不再向会话插入伪造 user 消息；首条可见内容是 Agent 诊断报告。

30.7 Restart Persistence 硬验收
创建至少 2 个普通 Conversation；其中一个产生 5 条以上消息。
触发 synthetic Incident，生成 Diagnosis，并在 Incident Conversation 追问。
停止 API、monitor-worker、agent-worker、rag-worker，但保留 PostgreSQL/Milvus volume。
重新启动后，旧 Conversation、Message、Incident、Evidence、Diagnosis、Trace 必须全部恢复。
在旧 Conversation 再发一条消息，确认能够继续对话，而不是因为内存丢失创建新 thread。
30.8 RAG 本地硬验收
至少准备 CPU 高、PostgreSQL connection refused、Playwright/Chromium 异常三份运维手册，跑完整 ingestion/retrieval；再维护不少于 10 条固定 query 回归集。每个结果检查 document/version/chunk/page_range Citation 和 RetrievalTrace。Embedding 模型/维度改变时提升 `ONCALL_KNOWLEDGE_INDEX_VERSION` 并重建，不复用旧索引。
30.9 真实 Agent / Feishu 硬验收
普通 SOP 问题应优先合理使用 search_knowledge；实时状态问题应选择实时 Tool。
Incident 报告必须包含故障概况、Evidence、root cause、confidence、具体 remediation、verification、risks、knowledge refs/unknowns。
无充分证据时降低 confidence 并明确 unknowns，禁止凭空编造“已确认根因”。
飞书主动 interactive card 成功后，回复该消息必须回到原 incident_id/conversation_id 并进入 FOLLOW_UP。
模拟发送失败，验证 retry/backoff/dead；cooldown 抑制重复 diagnosis，但 recovery 必须发送。
