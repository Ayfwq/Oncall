1. 结论摘要
本报告将 Oncall 定义为一个本地优先、可扩展的 AI SRE 平台。V1 支持同一台主机上的多个被监控项目；提供 ChatGPT 式多会话 Web、飞书双向对话、完整 RAG、确定性主动监测、Incident 管理，以及统一 OncallAgent 的调查与故障报告能力。
最终推荐：采用“模块化单体（Modular Monolith）+ 多运行进程 + PostgreSQL 持久化协调”。LangGraph 仅承担 Agent 编排；Monitoring Engine、RAG ingestion、业务数据与通道层均保持独立模块。

2. 产品约束与架构目标
V1 范围：单用户、本机多项目、只读诊断；远程服务器与自动修复延期。
统一 Agent：只有一个 OncallAgent，支持 CHAT / INVESTIGATE / FOLLOW_UP 三种运行模式。
主动报告：发生 Incident 后生成完整监测报告，必须包含证据、根因、解决步骤、风险与恢复验证步骤。
持续追问：Web 或飞书中的 Incident 会话可继续追问；重启服务后历史会话与 Incident 不丢失。
知识底座：RAG 是共享知识服务，不是 Agent 私有记忆；聊天和调查共用同一检索服务。
稳定性：监控检测不依赖 LLM；LLM 只在问答、调查、解释、生成诊断时参与。

6. RAG 与知识库
Upload -&gt; Validate -&gt; Checksum/Dedupe -&gt; Docling Parse       -&gt; DoclingDocument(JSON) + Normalized Markdown       -&gt; Structure-aware Chunk (HybridChunker baseline)       -&gt; Metadata Enrichment -&gt; Dense Embedding       -&gt; Milvus Dense + BM25 IndexQuery -&gt; Normalize -&gt; [Dense top20 || BM25 top20]      -&gt; RRF Fusion (~30) -&gt; Rerank -&gt; Top5 + Threshold      -&gt; Citation Package -&gt; Agent      -&gt; (low quality only) one-time LLM query rewrite and retry
Docling：作为 ingestion 统一解析层，保留结构、标题、表格等信息；HybridChunker 以层次结构为基础并做 token-aware 调整。[R5][R6]
Milvus：同时承载 dense 向量与原生 BM25 sparse 检索，可执行 hybrid search。[R8][R9]
事实源：原始文件 + canonical DoclingDocument/Markdown + PostgreSQL 元数据是事实源；Milvus 是可重建索引。
Chunk 原则：SOP 优先保持标题路径、编号步骤、表格/代码块完整；默认 600–900 tokens，结构边界优先于固定长度。
版本管理：相同 checksum 跳过；更新创建 version；embedding 模型/维度变化时创建新的 embedding_profile/collection namespace，禁止自动 drop 旧集合。

16.1 RC1 技术约束
版本标记采用 1.0.0-rc1；只有本地 Release Gate 全绿后才改为 1.0.0。
当前构建环境无法访问 PyPI/npm registry，不能生成真实 uv.lock/package-lock.json；禁止伪造锁文件。目标机器首次成功安装后必须生成。
真实 LLM API、Embedding、Rerank、飞书 Secret 只放目标机器 .env，不写入源码或文档。
Milvus collection 名包含 knowledge index version + embedding dimension。Embedding 模型、维度或 schema 语义变化时创建新索引并从 canonical source 重建，不自动 drop 旧索引。
开发 Hash Embedding/lexical rerank 仅用于无 Key 的工程联调，不作为生产检索质量承诺。
V1 继续维持 read-only Agent；任何 restart/kill/write-SQL 等 Action Tool 必须进入后续 ADR + human approval。
