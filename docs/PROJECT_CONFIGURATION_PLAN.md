# 项目配置与接入规划

## 目标

一个 Project 不是一组随意填写的字段，而是一个可验证的监控目标：

`基本信息 → 监控范围 → 数据源连接 → 指标与告警 → 采集测试 → 启用`

保存只能产生“可解释的配置状态”，不能把缺少目标、无效地址或无效规则的半成品交给监控 worker。

## 配置模型

- **Project**：名称、用途说明、绑定服务器、采集周期、启停状态。
- **Target**：远程服务器 Node/DCGM Exporter、Python 健康检查和 Python `/metrics`；每个服务器可被多个项目复用。
- **Signal**：从已支持的指标目录选择采集指标，不允许前端随意拼写。
- **Rule**：指标、资源键、固定阈值或历史基线模式、触发/恢复参数、持续次数和级别。
- **Validation**：格式校验、跨字段校验、连接/采集 dry-run；连接密码只写入加密字段，不回显。

## 创建流程（当前版本）

1. 在创建页创建远程 Python 项目，填写健康检查地址和 Prometheus `/metrics`；两个地址都是必填项。
2. 后端 `POST /api/projects/onboard/python` 绑定已配置服务器，保存健康检查、HTTP 白盒指标、Python process 指标和基础规则；GPU 根据服务器是否配置 DCGM 自动加入。
3. 新项目默认停用；进入详情页执行 dry-run，确认指标存在后再启用。
4. 当前远程 Python 入口不再要求用户配置日志、Docker、数据库或本机 PID；规则由固定阈值、历史基线和连续次数自动生成。
5. 当前默认规则由后端统一生成；用户不需要手工填写每个指标名称。

## 当前版本与后续拆分

- 当前实现：远程 Python 页面只保留服务器、健康检查和 `/metrics` 三个采集入口；测试采集不落库。
- 后续增强：可在不改变当前采集契约的前提下增加配置版本、差异对比、回滚、凭证轮换和维护窗口。

## 完成标准

- 新建项目至少有明确名称和采集周期。
- 每个启用的 target 都能说明采集失败原因。
- 每条启用规则都引用已注册指标，触发/恢复参数有效。
- 保存、测试、启用三个动作状态独立，不能用“保存成功”冒充“监控已生效”。
- 飞书、Web 和 worker 使用同一份 Project runtime config，不能各自解释一套字段。
